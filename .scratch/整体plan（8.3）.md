**日期：** 2026-08-03
**范围：** ESP32-S3 固件、MaixCam/K210 视觉端、本地 Python 实时服务、云端 Java/Python 服务、Vue 管理台
**目标：** 明确当前项目主线、真实完成度、关键断点及后续实施顺序，为设备联调和云端部署提供统一依据。

---

## 一、项目定位

智岁灵犀（Resona）是在 xiaozhi-esp32 语音助手基座上扩展的助老陪护机器人原型。项目的差异化能力不是普通语音聊天，而是：

1. K210/MaixCam 从面部表情提取四类视觉情绪概率；
2. ESP32-S3 从语音中提取音高、能量等情绪特征；
3. 使用 Dempster-Shafer（D-S）证据融合得到综合情绪与模态冲突度；
4. 将实时情绪注入云端 LLM，使回复语气更具关怀性；
5. 将情绪历史、预警、老人档案、关怀提醒等数据呈现在家属/管理员 Web 管理台。

隐私设计原则是原始人脸和音频不上传云端，只上传情绪概率、冲突度、设备标识及必要的文本意图。系统输出只能作为陪护与人工复核线索，不应表述为医学诊断。

## 二、目标数据链路

```text
MaixCam/K210 摄像头 --FER 表情概率--UART--┐
                                           ├─ ESP32-S3 D-S 融合
ESP32 麦克风 --音高/RMS 语音情绪-----------┘
                      │
           表情显示 + emotion_state 上报
                      │ WebSocket/MCP
                      v
       本地 Python ASR / LLM / TTS 服务
          │                    │
   情绪注入 LLM 提示词      异步写云端
          │                    v
     共情语音回复       MySQL + Java/Vue 管理台
```

系统包含两个闭环：

- **实时交互闭环：** 设备采集 -> 情绪融合 -> LLM 情绪上下文 -> TTS 回复；
- **照护数据闭环：** 情绪上报 -> 持久化 -> 历史/统计/预警 -> 家属或管理员处理。

当前第一个闭环部分可运行，第二个闭环尚未真正跑通。

- 数据库已定义 9 张养老业务表。

### 4.2 部分实现

- SER 当前是音高/RMS 启发式分类，MFCC/TFLite 推理仍是占位；
- FER 与 UART 视觉程序已写出，但仓库没有可部署的 `.kmodel`/`.mud` 模型；

- 前端新增页面已接好 API 形式，但后端多数没有业务实现；
- SNR、Lux 和动态可靠度存在于接口设计中，ESP32 尚未实际上报。

### 4.3 尚未形成闭环

- 最新现场日志没有任何视觉 JSON 包或命令响应，当前实机本质上是语音单模态；
- Java 新增 Controller 基本只返回空 `Result`，没有 Service/DAO；
- 云端轻量 Python 的历史和统计接口返回空数据；
- 安全关键词检测、通知推送、关怀提醒调度尚未实现；
- 新增业务页面不能稳定完成真实 CRUD。

## 五、关键技术断点

### P0-1：高冲突预警在当前参数下不可达

视觉和音频 BPA 的 singleton 总质量分别被置信度折扣为 `0.75` 和 `0.70`，因此冲突因子理论最大值不超过：

```text
K_max = 0.75 * 0.70 = 0.525
```

当前高冲突阈值却是 `0.85`，所以核心的 `high_conflict` 分支不会触发。必须重新定义冲突指标或在折扣前计算原始分布冲突，再通过实验数据确定阈值。

### P0-2：情绪历史落库路径断裂

本地 Python 把情绪写到硬编码的 `/resona/emotion/write`，但当前云端轻量 Python 没有该路由；Java 提供的是 `/emotion/history`，且实现为空。结果是：

- 实时情绪可能在内存中可见；
- 历史数据不会稳定写入 MySQL；
- 历史曲线和统计页面只能显示空数据。

应统一为一个受认证的写入端点，并实现查询、分页与聚合。

### P0-3：视觉链路没有真实输入

现场 ESP32 日志显示 UART 已初始化并持续发送 `GET_STATE`，但没有收到视觉板响应或情绪包。优先检查：

1. MaixCam/K210 是否独立供电；
2. 实际硬件型号和 UART 引脚；
3. SD 卡是否部署新版 `main.py`、`uart_comm.py`、`fer_engine.py`；
4. 模型文件是否存在且格式正确；
5. TX/RX 是否交叉并共地；
6. 视觉板启动日志是否报模型或 Python API 不兼容。

### P1-1：CRC 校验依赖重新序列化

视觉端对 `ujson.dumps()` 原始文本计算 CRC；ESP32 解析后通过 cJSON 重新序列化再校验。浮点格式、空值表达或序列化行为不同可能造成误判。

建议定义固定字段顺序的 canonical payload，或使用长度 + payload + CRC 的二进制帧。两端必须共享协议测试向量。

### P1-2：算法验证不足

- SER 是启发式规则，不是训练模型；
- D-S 动态 SNR/Lux 纠偏只完成实验设想；
- 仿真结果不能替代真实老人语音和表情数据验证；
- “隐性抑郁”只能作为风险提示，必须引入人工复核和误报控制。

### P1-3：配置和部署不可迁移

OTA、WebSocket、云端同步地址存在硬编码。当前固件只适用于指定热点网段，换网络后无法自动工作。地址、密钥、设备 ID 应进入分环境配置或安全的设备配置流程。

### P0-4：凭据泄露

现有交接文档、脚本和配置中存在服务器、数据库、管理员及第三方服务明文凭据。应立即轮换，并从 Git 历史和可分发交付物中清除。后续统一改为环境变量或服务器侧 Secret 文件。

### 阶段 A：工程基线与安全（P0）

**验收：** 新机器按 README 能拉取、配置、构建；仓库扫描无明文密钥。

### 阶段 B：视觉与端侧融合闭环（P0）

1. 确认视觉板型号、供电与串口；
2. 获取并验证人脸检测和 FER 模型；
3. 先运行 UART 回环/命令测试，再运行固定情绪包测试；
4. 改造 CRC 帧格式并增加协议测试向量；
5. ESP32 连续收到 `Pkt seq=` 后再开启 FER；
6. 修正冲突指标和阈值，用预制对立分布验证 `high_conflict` 可触发；
7. 补充时间窗对齐、平滑与 stale 状态测试。

**验收：** 视觉与语音都有效时 K 非零；拔掉任一模态能正确降级；高冲突样例能触发预警。

### 阶段 C：云端数据闭环（P0）

1. 定义唯一 `EmotionRecord` 数据契约；
2. 实现认证的写入、历史查询和统计接口；
3. Python 使用配置中的 manager API 地址和密钥，禁止硬编码；
4. 实现幂等键（设备 ID + 设备时间/序列号）避免重复写入；
5. 前端实时页走 Python 内存接口，历史/统计走持久化接口；
6. 增加端到端测试：模拟设备上报 -> MySQL -> Web 查询。

**验收：** 上报一条情绪后可在数据库、历史 API 和前端曲线中看到同一记录。

### 阶段 D：养老业务闭环（P1）

按真实使用价值依次实现：

1. 高冲突/连续悲伤预警；
2. 老人档案与设备绑定；
3. 预警人工处理和备注；
4. 关怀提醒调度；
5. 紧急联系人通知；
6. 语料标注和用户反馈；
7. 安全关键词检测与升级处置。

### 阶段 E：验证与交付（P1）

1. 建立端侧协议、融合算法、Python API、Java Service 和前端 E2E 测试；
2. 使用非敏感志愿者数据做小样本验证；
3. 记录准确率、误报率、漏报率、延迟、内存和断网降级表现；
4. 明确产品提示语、人工复核流程和数据保留策略；
5. 形成可重复部署包、运维手册和演示脚本。
